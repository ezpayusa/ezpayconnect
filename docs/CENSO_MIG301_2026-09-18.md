## La fabrica de default privilege

Estado de hoy, crudo de `pg_default_acl`:

```
objtype='f' (FUNCIONES), rol postgres, schema public:
  postgres=X/postgres  anon=X/postgres  authenticated=X/postgres  service_role=X/postgres

objtype='f' (FUNCIONES), rol supabase_admin, schema public:
  postgres=X/supabase_admin  anon=X/supabase_admin  authenticated=X/supabase_admin  service_role=X/supabase_admin

objtype='S' (SECUENCIAS), rol postgres, schema public:
  postgres=rwU/postgres  anon=rwU/postgres  authenticated=rwU/postgres  service_role=rwU/postgres
```

**Sigue abierta.** Cada funcion nueva de `public` nace ejecutable por `anon`. Es la fabrica que
produjo las 62 del censo, y la razon por la que la mig 300 tuvo que usar `CREATE OR REPLACE` en
vez de `DROP`+`CREATE` (un DROP+CREATE las habria hecho renacer con `anon=X`).

El comando, mismo patron que la mig 298 uso para tablas, adaptado a funciones:

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC;
ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public REVOKE EXECUTE ON FUNCTIONS FROM anon;
```

Dos cosas medidas en la 298 que aplican igual aca:

- La entrada de **`supabase_admin` no se puede tocar** desde la conexion del CLI: `ALTER DEFAULT
  PRIVILEGES FOR ROLE supabase_admin` da `42501` porque `postgres` no es superuser ni miembro de
  ese rol. **No importa en la practica**: un default privilege aplica segun QUIEN CREA el objeto, y
  las 266 funciones de `public` las crea `postgres`. Queda inerte, y una probe deberia vigilarlo.
- **`REVOKE EXECUTE` no alcanza con PUBLIC solo**: `anon` tiene su propia entrada en el ACL por
  defecto, asi que hay que nombrarlo aparte. Es lo mismo que paso con las tablas en la 298.

**Fuera de alcance salvo que Oscar diga lo contrario:** las SECUENCIAS (`objtype='S'`) tambien le
dan `rwU` a `anon`. `U` es USAGE, que permite `nextval()` — o sea consumir ids de cualquier
secuencia. No se midio si es explotable; queda anotado.

### Las dudosas, una por una

**`liberar_examen_al_paciente(p_examen_id integer)`**

BOMBA LATENTE, no explotable hoy. Su gate tiene el MISMO veneno que obtener_contexto_visita (`v.medico_id = auth.uid()` suelto dentro de un OR). Medido: 0 examenes con medico_id NULL, por eso da PT002 a los dos actores. El dia que entre un examen sin medico asignado se abre igual que se abrio obtener_contexto_visita con las 5 citas sin medico. Merece el COALESCE aunque el REVOKE ya lo tape.

**`liberar_orden_al_paciente(p_orden_id uuid)`**

Mismo caso que liberar_examen_al_paciente: las condiciones de autoria viven en el WHERE del UPDATE (fail-closed por construccion), pero comparte el patron. Medido: 0 filas afectadas para los dos actores.

**`registrar_proveedor(p_nombre_empresa text, p_tipo text, p_ruc_nit text, p_pais_id uuid, p_ciudad text, p_direccion text, p_email_contacto text, p_telefono text, p_nombre_completo text, p_email text)`**

Unica con call-site alcanzable desde una pantalla publica (ProveedorRegistro / ProveedorLogin comparten `useProveedorAuth`). PERO la llamada ocurre DESPUES de `supabase.auth.signUp()`, o sea ya con sesion, y su primera linea es `IF v_user_id IS NULL THEN RAISE 'Usuario no autenticado'`. Medido: con anon lanza P0001. Si el alta dependiera del acceso anon, HOY ya estaria rota. Revocar cambia el error de P0001 a 42501; no cambia que falle.

### Lo que este recon NO decide

De las 60, **26 no tienen un solo call-site** en `src/`. Para esas la pregunta no es solo si
sacarles `anon`, sino si tambien deberian perder `authenticated`. Eso es un frente aparte y mas
delicado (algunas las llaman otras funciones, y ahi el REVOKE no rompe nada; otras pueden estar
esperando un consumidor que todavia no existe). No lo resolvi en este recon.
